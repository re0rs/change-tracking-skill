# 变更追踪最佳实践指南

## 概述

本指南定义了使用 Change Tracking Skill 生成变更记录的最佳实践，确保文档质量和信息完整性。

## 何时生成变更记录

### 建议生成的场景

1. **Bug 修复完成后**
   - 修复了影响功能的问题
   - 修复了安全漏洞
   - 修复了性能问题

2. **新功能开发完成后**
   - 完成了独立的功能模块
   - 完成了 API 接口开发
   - 完成了重要的业务逻辑

3. **重大重构后**
   - 架构调整
   - 模块拆分或合并
   - 代码结构优化

4. **接口变更后**
   - API 接口签名变更
   - 数据结构变更
   - 配置格式变更

### 可以跳过的场景

1. 简单的代码格式化
2. 注释修改
3. 变量重命名（无逻辑变更）
4. 依赖小版本升级（无 breaking changes）

## 文档质量标准

### 变更概要

- ✅ 一句话说明变更目的
- ✅ 包含关键动词（修复、添加、优化、重构）
- ❌ 避免过于笼统（如"更新代码"）

### 详细描述

- ✅ 说明变更背景
- ✅ 说明实现方式
- ✅ 说明设计决策
- ❌ 避免重复概要内容

### 具体改动

- ✅ 每处改动都有位置说明
- ✅ 每处改动都有原因说明
- ✅ 位置使用行号或函数名
- ❌ 避免只列出文件名

### 根因分析（Bug 修复）

- ✅ 清晰描述问题症状
- ✅ 深入分析根本原因
- ✅ 说明代码层面的问题
- ❌ 避免只说"代码写错了"

### 踩坑记录

- ✅ 记录每一次误判
- ✅ 记录每一次误改
- ✅ 分析误判/误改的原因
- ❌ 避免遗漏重要的调试弯路

### 影响分析

- ✅ 列出所有接口变更
- ✅ 列出所有数据结构变更
- ✅ 列出所有受影响模块
- ✅ 严格检查后才标注"无外部影响"

## 常见问题处理

### Git 信息不可用

**场景**：不在 Git 仓库中工作

**处理**：
- 继续生成文档
- 在元信息中标注"信息不可用"
- 建议用户初始化 Git 仓库

### 大量文件修改

**场景**：一次修改涉及数十个文件

**处理**：
- 只详细记录核心文件的改动
- 批量修改使用摘要统计
- 提供 commit hash 供查看完整 diff

### 多次修复同一问题

**场景**：问题反复出现，多次修复

**处理**：
- 在踩坑记录中详细记录每次尝试
- 分析为什么之前的修复不彻底
- 总结问题的根本原因

### 用户不确定是否需要记录

**场景**：用户询问是否应该生成

**建议判断标准**：
- 会影响其他人的代码 → 建议生成
- 会影响系统行为 → 建议生成
- 只是个人偏好调整 → 可以跳过

## 标签使用规范

### 常用标签

| 标签 | 适用场景 |
|------|---------|
| API | 接口相关修改 |
| 数据库 | 数据模型、查询相关 |
| 缓存 | 缓存相关优化 |
| 安全 | 安全漏洞修复、权限相关 |
| UI | 界面相关修改 |
| 性能 | 性能优化相关 |
| 配置 | 配置文件相关 |
| 测试 | 测试相关修改 |

### 标签数量

- 建议：2-5 个标签
- 过少：不便于检索
- 过多：失去分类意义

## 文件命名规范

### 格式

```
YYYY-MM-DD_HHmmss_简短描述.md
```

### 简短描述

- 2-4 个中文词
- 或 3-5 个英文单词
- 描述核心改动内容
- 避免使用特殊字符

### 示例

✅ 好的命名：
- `2024-03-15_143022_修复登录验证.md`
- `2024-03-15_160530_添加用户权限.md`

❌ 不好的命名：
- `2024-03-15_143022_fix.md`（太笼统）
- `2024-03-15_143022_修复用户登录时因为密码验证逻辑错误导致的问题.md`（太长）

## 版本控制建议

1. 将 `docs/change-logs/` 目录纳入 Git 管理
2. 变更记录随代码一起提交
3. 在 commit message 中引用变更记录
4. 定期归档历史记录（如按月份整理）
